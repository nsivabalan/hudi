# Hudi 0.14.0 — recovering from cleaner / archival OOM on a large MoR table

## Problem statement

Customer ABC is running Apache Hudi 0.14.0 on a large MoR table with the
following shape:

- Ingestion is bulk-insert only (no upserts; the table is too large for it).
- Writes land every 15 minutes with inline compaction and inline cleaning.
- No clustering is in place.
- `delete_partition` is issued occasionally; cleaner is the mechanism that
  actually reclaims those files.
- Partitioning by `cust_id`, ~1000–5000 partitions.
- Commit retention was set to ~30 days, so the active timeline retained a very
  long window of commits.

Symptom: at some point cleaning and archival could no longer run. The active
timeline had grown to roughly 2 GB on disk, and an ordinary bulk-insert write
failed during `autoCleanOnCommit` while the cleaner was preparing its plan —
before any executor had walked a partition:

```
Exception in thread "main" java.lang.OutOfMemoryError:
    Required array length 2147483639 + 10 is too large
  at java.io.ByteArrayOutputStream.ensureCapacity(ByteArrayOutputStream.java:100)
  at java.io.ObjectOutputStream.writeObject(ObjectOutputStream.java:350)
  at org.apache.spark.serializer.JavaSerializerInstance.serialize(JavaSerializer.scala:115)
  at org.apache.spark.util.ClosureCleaner$.ensureSerializable(ClosureCleaner.scala:441)
  at org.apache.spark.SparkContext.clean(SparkContext.scala:2688)
  at org.apache.spark.rdd.RDD.map(RDD.scala:414)
  at org.apache.hudi.client.common.HoodieSparkEngineContext.map(HoodieSparkEngineContext.java:116)
  at org.apache.hudi.table.action.clean.CleanPlanActionExecutor.requestClean(CleanPlanActionExecutor.java:122)
  ...
  at org.apache.hudi.client.BaseHoodieWriteClient.autoCleanOnCommit(BaseHoodieWriteClient.java:606)
  at org.apache.hudi.client.BaseHoodieWriteClient.commitStats(BaseHoodieWriteClient.java:255)
```

To keep the pipeline running, customer ABC disabled cleaner and archival.
That stops the OOM but leaves files from deleted partitions on storage and
lets the active timeline keep growing.

## Root cause

Two issues compound, and they line up directly with the stack trace.

1. **Cleaner planning on a bulk-insert table has no incremental anchor, so it
   plans across every partition.** On 0.14.0, when no recent clean commit is
   present, the clean planner has nothing to scope "what changed since the
   last clean" against, and `CleanPlanner.getPartitionPathsToClean` returns
   the full partition list. For an append-only / bulk-insert workload with
   only sporadic `delete_partition` events, the vast majority of those
   partitions have nothing to clean — but the planner still includes them
   all in the list it hands to Spark next.

2. **That full partition list is fed to a Spark `map` whose closure captures
   the entire `CleanPlanner`.** Concretely, at `CleanPlanActionExecutor.java:122`
   the planner does:

   ```java
   context.map(partitionsToClean,
               partitionPath -> Pair.of(partitionPath,
                                        planner.getDeletePaths(partitionPath, earliestInstant)),
               cleanerParallelism);
   ```

   The lambda references `planner`, so Spark's `ClosureCleaner` has to
   serialize the `CleanPlanner` instance along with the closure before the
   job is dispatched. `CleanPlanner` carries a fully resolved file-system
   view of the table — every partition's file groups, file slices, and the
   savepoint/commit metadata it has already loaded for planning. At the
   scale of thousands of partitions × thousands of commits on the active
   timeline, that serialized object crosses Java's hard 2 GB single-object
   byte-array limit. `ByteArrayOutputStream.ensureCapacity` then throws the
   `OutOfMemoryError` shown above. **It is not a JVM heap problem.** Heap
   has nothing to do with it; the JVM refuses to allocate a single array
   bigger than `Integer.MAX_VALUE - 8` bytes.

The trigger in the failing run was an ordinary inline bulk-insert: the
write committed, `BaseHoodieWriteClient.commitStats` called
`autoCleanOnCommit`, the cleaner tried to build its plan, and the planning
closure blew up before any executor task ran. So while the *symptom* shows
up as "cleaning fails," the *cause* is the planner trying to ship a
table-wide view of state to Spark when the only thing it actually needs to
look at is a small recent slice.

Because of (1), simply re-enabling cleaner on plain 0.14.0 does not work —
the very first plan would still include the entire partition space, and (2)
would fire again.

## The cleaner window and ECTR

The cleaner's job is bounded by a single timestamp on the timeline:
`earliestCommitToRetain` (ECTR). Everything strictly older than ECTR is
eligible to be cleaned; everything at-or-after ECTR is kept. Each completed
clean writes ECTR into its plan and into its `HoodieCleanMetadata`. The
**next** clean reads it back, and that defines how far the planner has to
look — that's the whole point of this section, and it's why the recovery
plan in the next section is built around moving ECTR forward.

There are three states worth picturing.

### 1. Today (stock 0.14.0, cleaner disabled)

```
                                       ECTR was anchored here, long ago,
                                       before cleaner was turned off.
                                       |
  archived | <----------------- active timeline ----------------> |
  ---------+--------+--------+--------+--------+---------------+---
           t_old    ...     ECTR              ...             now
                            ^                                  ^
                            |                                  |
                            window `[ECTR, now]` covers        thousands
                            thousands of partitions ×          of commits
                            thousands of commits.              accumulated
                            CleanPlanner loads file-system     while
                            view for the whole window, and     cleaner
                            the closure that captures that     was off.
                            view overflows the 2 GB array
                            limit when Spark tries to
                            serialize it for dispatch.
```

The cleaner's planning window is `[ECTR, now]`. Because the window is
huge, `CleanPlanner` materializes a table-wide view, and the closure that
captures that view overflows the 2 GB single-object array limit during
`ClosureCleaner.ensureSerializable` — *before* any executor task runs.

### 2. After Step 1 — one-time partition-filtered clean

```
                                                       new ECTR, written
                                                       by the targeted
                                                       clean (real, not
                                                       empty).
                                                       |
  archived  | <----------- active timeline ----------> | <-- retain -->
  ----------+-----+-----+-----+-----+-----+-----+-----+-----+-----+----
                                                      ^                ^
                                                      ECTR             now
                                                      |
                                                      Only partitions in
                                                      hoodie.clean.partition.filter.selected
                                                      were inspected — the rest of the
                                                      partition space was skipped.
                                                      The clean still writes ECTR
                                                      globally so the next clean has
                                                      a usable anchor.
```

ECTR has jumped forward to roughly "now minus retention." The planner's
window is now small. The next clean — incremental — only has to walk
partitions modified since this ECTR.

### 3. Steady state — empty cleans roll ECTR forward

```
                                  empty cleans (no files deleted) roll ECTR
                                  forward on each cadence tick, so the
                                  window stays bounded even on a
                                  bulk-insert-only workload.
                                  |
                                  v
  ----+----E----+----+----E----+----+----E----+----+----E----+--->
       \________/    \________/    \________/    \________/
       window         window         window         window
       bounded by     bounded by     bounded by     bounded by
       the empty-     the empty-     the empty-     the empty-
       clean          clean          clean          clean
       cadence        cadence        cadence        cadence
```

Each `E` is either an empty clean (`hoodie.write.empty.clean.create.duration.ms`
fired with nothing to delete) or a real clean. Both write ECTR forward to
roughly `latest_commit - retain_commits`. The planner's working set never
grows beyond one cadence interval × the few partitions touched in it, which
is what keeps the Spark closure small enough to dispatch.

A branch on top of Apache Hudi 0.14.0:

`release-0.14.0-clean-enhancements`

It adds the following on top of stock 0.14.0:

| Change | What it provides |
|---|---|
| Cleaner / savepoint interplay fix (HUDI-7104) | Fixes an incremental-clean edge case involving savepoints. Prerequisite for the empty-clean support below. |
| Empty-clean support | New config `hoodie.write.empty.clean.create.duration.ms`. Lets the cleaner emit "empty" clean commits on append-only tables. Those empty commits roll `earliest_commit_to_retain` forward, so the next real clean only has to look at partitions modified after the most recent empty clean. |
| Partition filter for full clean (apache/hudi PR #17550) | New configs `hoodie.clean.partition.filter.regex` and `hoodie.clean.partition.filter.selected`. Allows a one-time full clean scoped to a specific set of partitions instead of the whole table. |
| `PartitionsTouchedAfterECTRTool` | Standalone Java utility that reads the active timeline and emits the deduplicated list of partitions that were replaced (replaceCommit) or cleaned at/after the most recent clean's ECTR. Plain commit/deltaCommit ingestions are intentionally excluded. Feeds directly into `hoodie.clean.partition.filter.selected`. |

## Recovery plan

There are two steps. Step 1 is a one-time operation that unblocks the current
state. Step 2 is the steady-state configuration to switch to afterward so
the problem does not recur.

### Step 1 — one-time targeted clean

Goal: clean only the partitions that actually have garbage — the ones touched
by `delete_partition` (and any other replace / insert-overwrite) within the
current active timeline — without scanning the rest of the table.

1. Build the list of partitions that appear as touched or replaced in the
   active timeline. The replace-commit and `delete_partition` metadata in the
   timeline carries this information.

   The branch ships a standalone tool that does this:
   `org.apache.hudi.utilities.PartitionsTouchedAfterECTRTool`. It reads the
   most recent completed clean's `earliestInstantToRetain` (ECTR) from the
   active timeline and emits the deduplicated set of partitions that were
   replaced (replaceCommit — including `insert_overwrite` and
   `delete_partition`) or cleaned at or after that instant. If no completed
   clean exists (or its plan has no ECTR, e.g. an empty clean), the tool
   scans the entire active timeline. Only completed `replaceCommit` and
   `clean` instants are considered — plain `commit` / `deltaCommit`
   ingestions that only add new file groups are out of scope.

   Sample invocation:

   ```bash
   java -cp hudi-utilities-bundle.jar \
     org.apache.hudi.utilities.PartitionsTouchedAfterECTRTool \
     --base-path s3://bucket/path/to/table \
     --output-file /tmp/partitions.txt
   ```

   The output file (one partition per line) feeds directly into
   `hoodie.clean.partition.filter.selected` in step 2 below.

2. Run cleaner once, manually, with the following configs:

   - `hoodie.clean.automatic=false` while the catch-up run is driven manually.
   - `hoodie.clean.incremental.mode.enabled=false`.
     **This is required.** The new partition filter only applies when
     incremental clean mode is off; with incremental mode on, the filter is
     rejected at planning time.
   - Either
     `hoodie.clean.partition.filter.selected=<comma-separated partition list>`
     or, if that list is unwieldy,
     `hoodie.clean.partition.filter.regex=<regex>`.
     If both are set, the selected list takes precedence.

3. Let the clean run to completion. Once it finishes, the active timeline has
   a completed clean commit that anchors `earliest_commit_to_retain`. From
   this point on, future incremental clean plans have a bounded window to
   look at.

### Step 2 — steady-state configuration

After Step 1 completes, switch the pipeline to the configuration below and
re-enable inline cleaning and archival. From here on, the cleaner only looks
at partitions modified after the most recent clean (real or empty), and the
active timeline stays bounded.

The table below lists the keys and what each one does; values should be
chosen to match the customer's SLA.

| Config | Purpose |
|---|---|
| `hoodie.write.empty.clean.create.duration.ms` | Emits empty clean commits when the cleaner has no real work to do. On a bulk-insert table this is the normal case. These empty commits keep `earliest_commit_to_retain` rolling forward so the next real clean planner only ever looks at recent partitions. Pick a duration that bounds how far back any future real clean could ever have to scan. |
| `hoodie.cleaner.commits.retained` | Once empty cleans are anchoring `earliest_commit_to_retain`, the cleaner no longer needs to retain a 30-day window of clean commits. Reduce this to a smaller value sized to the customer's SLA. |
| `hoodie.clean.incremental.mode.enabled` | Restore to the default (`true`). The planner will then only inspect partitions modified since the last clean. |
| `hoodie.keep.min.commits` / `hoodie.keep.max.commits` | Align archival with the new cleaner retention so the active timeline is bounded and archival can resume. |
| `hoodie.compact.inline.max.delta.commits` | MoR-specific: controls log-file fan-out. Not the root cause of the OOM, but worth reviewing alongside the cleaner/archival settings. |

### Why this works long-term

- Empty clean commits push `earliest_commit_to_retain` forward even when there
  is nothing to clean. On a bulk-insert pipeline this is the common case, and
  it is exactly what was missing on stock 0.14.0.
- After a `delete_partition` runs, the cleaner doesn't necessarily fire on the
  very next commit — it fires once the cleaner threshold is met. When that
  first post-threshold cleaner run does fire, it only needs to inspect
  partitions modified since the last (empty or real) clean, which is bounded
  by the empty-clean cadence, not by the total partition count.
- The cleaner's `partitionsToClean` list and the `CleanPlanner` view captured
  by its planning closure stay small. The closure that Spark's
  `ClosureCleaner` has to serialize before dispatching the cleaner job
  comfortably fits well under the 2 GB single-object array limit.

## How to consume the branch

The branch is published as `release-0.14.0-clean-enhancements`. Build the
`hudi-utilities-bundle` from this branch and use it for both the
`PartitionsTouchedAfterECTRTool` invocation and the targeted cleaner run in
Step 1. For Step 2 the customer can either continue running on this branch
or upgrade to a release that contains all of these changes upstream.
