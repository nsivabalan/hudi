# Hudi 0.14.0 — recovering from cleaner / archival OOM on a large MoR table

## Problem statement

You are running Apache Hudi 0.14.0 on a large MoR table with the following
shape:

- Ingestion is bulk-insert only (no upserts; the table is too large for it).
- Writes land every 15 minutes with inline compaction and inline cleaning.
- No clustering is in place.
- `delete_partition` is issued occasionally; cleaner is the mechanism that
  actually reclaims those files.
- Partitioning by `cust_id`, ~1000–5000 partitions.
- Commit retention was set to ~30 days, so the active timeline retained a very
  long window of commits.

Symptom: at some point cleaning and archival could no longer run. The active
timeline had grown to roughly 2 GB on disk, and the cleaner job failed during
Spark task dispatch:

```
Exception in thread "main" java.lang.OutOfMemoryError:
    Required array length 2147483639 + 231 is too large
  at java.io.ByteArrayOutputStream.ensureCapacity(...)
  at java.io.ObjectOutputStream$BlockDataOutputStream.drain(...)
  at org.apache.spark.serializer.JavaSerializationStream.writeObject(...)
  at org.apache.spark.util.ClosureCleaner$.ensureSerializable(ClosureCleaner.scala:441)
  at org.apache.spark.util.ClosureCleaner$.clean(ClosureCleaner.scala:416)
  ...
```

To keep the pipeline running you disabled cleaner and archival. That stops the
OOM but leaves files from deleted partitions on storage and lets the active
timeline keep growing.

## Root cause

Two issues compound:

1. **Active timeline growing unbounded.** With cleaner and archival both off,
   every 15-minute bulk-insert commit accumulates on the active timeline. At
   the scale of thousands of partitions times thousands of commits, the
   serialized state pushed into Spark closures crosses Java's hard 2 GB
   byte-array limit. That is the limit the stack trace above is hitting — it
   is not a JVM heap problem, it is a single-object size limit on the
   serialized closure that carries the timeline state.

2. **Cleaner planning on a bulk-insert table scans every partition.** On
   0.14.0, when there is no recent clean commit, the clean planner has no
   anchor for "what changed since the last clean" and has to inspect every
   partition. For an append-only / bulk-insert workload with only sporadic
   `delete_partition` events, the vast majority of those partitions have
   nothing to clean — but the planner still has to walk them, which is what
   causes the OOM the next time cleaning is re-enabled.

Because of (2), simply re-enabling cleaner on plain 0.14.0 does not work — the
very first plan would have to scan the entire partition space.

## What we are shipping

A branch on top of Apache Hudi 0.14.0:

`release-0.14.0-clean-enhancements`

It adds the following on top of stock 0.14.0:

| Change | What it gives you |
|---|---|
| Cleaner / savepoint interplay fix (HUDI-7104) | Fixes an incremental-clean edge case involving savepoints. Prerequisite for the empty-clean support below. |
| Empty-clean support | New config `hoodie.write.empty.clean.create.duration.ms`. Lets the cleaner emit "empty" clean commits on append-only tables. Those empty commits roll `earliest_commit_to_retain` forward, so the next real clean only has to look at partitions modified after the most recent empty clean. |
| Partition filter for full clean (apache/hudi PR #17550) | New configs `hoodie.clean.partition.filter.regex` and `hoodie.clean.partition.filter.selected`. Lets you run a one-time full clean scoped to a specific set of partitions instead of the whole table. |
| `PartitionsTouchedAfterECTRTool` | Standalone Java utility that reads the active timeline and emits the deduplicated list of partitions whose file IDs were replaced at/after the most recent clean's ECTR. Feeds directly into `hoodie.clean.partition.filter.selected`. |

## Recovery plan

There are two steps. Step 1 is a one-time operation that unblocks the current
state. Step 2 is the steady-state configuration you switch to afterward so the
problem does not recur.

### Step 1 — one-time targeted clean

Goal: clean only the partitions that actually have garbage — the ones where
file IDs were replaced by `delete_partition` (or any other replace /
insert-overwrite / clustering) within your current active timeline — without
scanning the rest of the table.

1. Build the list of partitions where file IDs were replaced in the active
   timeline. The `replaceCommit` metadata in the timeline carries this
   information in `partitionToReplaceFileIds`.

   The branch ships a standalone tool that does this for you:
   `org.apache.hudi.utilities.PartitionsTouchedAfterECTRTool`. It reads the
   most recent completed clean's `earliestInstantToRetain` (ECTR) from the
   active timeline and emits the deduplicated set of partitions whose file IDs
   were replaced at or after that instant. If no completed clean exists (or
   its plan has no ECTR, e.g. an empty clean), the tool scans the entire
   active timeline. Only completed `replaceCommit` instants are considered,
   and only the partitions in `partitionToReplaceFileIds` — plain `commit` /
   `deltaCommit` instants and the new-write side of replace commits are
   ignored because they don't leave any files for the cleaner to reclaim.

   Sample invocation:

   ```bash
   java -cp hudi-utilities-bundle.jar \
     org.apache.hudi.utilities.PartitionsTouchedAfterECTRTool \
     --base-path s3://bucket/path/to/table \
     --output-file /tmp/partitions.txt
   ```

   The output file (one partition per line) feeds directly into
   `hoodie.clean.partition.filter.selected` in step 2 below.

2. Run cleaner once, manually, with the following configs:

   - `hoodie.clean.automatic=false` while you drive this catch-up run by hand.
   - `hoodie.clean.incremental.mode.enabled=false`.
     **This is required.** The new partition filter only applies when
     incremental clean mode is off; with incremental mode on, the filter is
     rejected at planning time.
   - Either
     `hoodie.clean.partition.filter.selected=<comma-separated partition list>`
     or, if that list is unwieldy,
     `hoodie.clean.partition.filter.regex=<regex>`.
     If both are set, the selected list takes precedence.

3. Let the clean run to completion. Once it finishes, the active timeline has
   a completed clean commit that anchors `earliest_commit_to_retain`. From
   this point on, future incremental clean plans have a bounded window to
   look at.

### Step 2 — steady-state configuration

After Step 1 completes, switch the pipeline to the configuration below and
re-enable inline cleaning and archival. From here on, the cleaner only looks
at partitions modified after the most recent clean (real or empty), and the
active timeline stays bounded.

We list keys and what each one does; pick values that match your SLA.

| Config | Purpose |
|---|---|
| `hoodie.write.empty.clean.create.duration.ms` | Emits empty clean commits when the cleaner has no real work to do. On a bulk-insert table this is the normal case. These empty commits keep `earliest_commit_to_retain` rolling forward so the next real clean planner only ever looks at recent partitions. Pick a duration that bounds how far back any future real clean could ever have to scan. |
| `hoodie.cleaner.commits.retained` | Once empty cleans are anchoring `earliest_commit_to_retain`, the cleaner no longer needs to retain a 30-day window of clean commits. Reduce this to a smaller value sized to your SLA. |
| `hoodie.clean.incremental.mode.enabled` | Restore to the default (`true`). The planner will then only inspect partitions modified since the last clean. |
| `hoodie.keep.min.commits` / `hoodie.keep.max.commits` | Align archival with the new cleaner retention so the active timeline is bounded and archival can resume. |
| `hoodie.compact.inline.max.delta.commits` | MoR-specific: controls log-file fan-out. Not the root cause of the OOM, but worth reviewing alongside the cleaner/archival settings. |

### Why this works long-term

- Empty clean commits push `earliest_commit_to_retain` forward even when there
  is nothing to clean. On a bulk-insert pipeline this is the common case, and
  it is exactly what was missing on stock 0.14.0.
- After a `delete_partition` runs, the cleaner doesn't necessarily fire on the
  very next commit — it fires once the cleaner threshold is met. When that
  first post-threshold cleaner run does fire, it only needs to inspect
  partitions modified since the last (empty or real) clean, which is bounded
  by your empty-clean cadence, not by the total partition count.
- The active timeline stays small, so closures dispatched to Spark stay well
  under the 2 GB single-object serialization limit.

## How to consume the branch

The branch is published as `release-0.14.0-clean-enhancements`. Build the
`hudi-utilities-bundle` from this branch and use it for both the
`PartitionsTouchedAfterECTRTool` invocation and the targeted cleaner run in
Step 1. For Step 2 you can either continue running on this branch or upgrade
to a release that contains all of these changes upstream.
